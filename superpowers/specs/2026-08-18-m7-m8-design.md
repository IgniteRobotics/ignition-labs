# M7 + M8 design record — build-order step 11

**Date:** 2026-08-18
**Build-order step:** 11 (spec §13) — *"M7, M8 templates | Mostly documents"*
**Governing sections:** §9.8 (M7), §9.9 (M8), §10 (no fixture for either), §11.1, §13

Step 11 ships two document-shaped milestones and one tooling fix that step 11 is the first
thing to require. Unlike steps 4–10, **nothing here is a Gradle project and nothing here has a
given test.** That single fact drives most of what follows, including the defect described in
§3, which is latent today and fires the moment M7 lands.

## 2. Decisions

### 2.1 `ai-code-review.yml` ships as a reference copy, not wired to CI

§9.8 asks for the workflow "copied from `Robot-2026`, so students meet AI-as-reviewer as a
running thing rather than a description." Running it *here* is the more literal reading and the
wrong one.

The setup is four files, not one — `.github/workflows/ai-code-review.yml`,
`.github/scripts/gemini-code-review.py`, `.github/scripts/requirements.txt`, and
`.github/prompts/code-review-prompt.md` — and the workflow requires a `GEMINI_CODE_REVIEW_KEY`
secret plus per-PR API spend.

Wiring it live in `ignition-labs` would mean configuring that secret on the student-facing
repository, paying per student pull request, and maintaining a second copy that drifts from the
one in `Robot-2026`. It buys nothing: **§9.8 already puts M7's work on a `Robot-2026` branch
with commit access, where this workflow already runs on every pull request.** A student at M7
meets AI-as-reviewer as a running thing because their own PR gets reviewed by it — in the real
repository, not a training mirror.

So all four files ship under `projects/m7-ai-assisted/` as read-and-copy reference, pinned to
`28ce5397d88275001d656dbb717d22cf9ac0150d`. This also serves the DoD item *"You read
`.github/prompts/code-review-prompt.md` and can name two standards in it"* — the file is in
front of the student rather than behind a repository they must go find.

### 2.2 Both copies of every M8 template survive, guarded by a check

§9.9 requires the deliverables in `student-deliverables.md` to become **real files** in
`templates/`. But that document already carries all six as fill-in-the-blank content inside
fenced blocks — so the milestone creates a second copy of each, and two copies of the same
template drift. This is the same failure `VisionPoseHelper` was consolidated to prevent in M5,
where the day the two copies disagree is the day the given test measures something the robot
does not do.

Consolidating to one copy is not available here the way it was in M5: **`templates/` is outside
`docs_dir`**, so MkDocs cannot render it. Replacing the fenced blocks with GitHub links would
thin a published curriculum document for its primary audience — students reading the site.

So both copies stay and `tools/templates_sync.py` makes drift impossible rather than unlikely,
following `tests_lock.py`'s established shape: a `verify` that exits non-zero naming the
offending file, pytest coverage, and CI wiring. This repository's answer to duplication it
cannot remove is a check that fails when the duplicate diverges, and this is that case.

### 2.3 `FEATURE-BACKLOG.md` is seeded from real candidates, mined from the pinned checkout

§9.8 requires "a mentor-maintained list of real, small, shippable features, so nobody spends
their M7 session choosing one." Inventing plausible-sounding features would defeat the "pick a
real, useful feature, not a toy" requirement as thoroughly as leaving the file empty.

Findings from `Robot-2026` at the pinned SHA are in §4. The file ships seeded and is explicitly
mentor-maintained: entries get consumed as students ship them, and the selection criteria
matter more than any particular entry.

### 2.4 One plan, two lanes, tooling fix serialized first

M7 touches only `projects/m7-ai-assisted/`. M8 touches `templates/`, `tools/templates_sync.py`,
`tests/`, `projects/m8-ownership/`, and `docs/programming/student-deliverables.md`. Disjoint —
two lanes, as in every prior step.

The `changed_projects.py` fix (§3) is a **serialized prerequisite**, not a lane. It is the thing
that breaks when either lane lands, so it cannot run concurrently with the work that trips it.

## 3. The defect step 11 is the first to require

`tools/changed_projects.py` documents itself as returning *"the sorted, deduplicated set of
standalone Gradle projects to build."* It does not check that they are Gradle projects. Any
changed path of the form `projects/<name>/<anything>` is selected.

Every directory under `projects/` has been a Gradle project until now, so the bug has never
fired. **M7 and M8 are the first that are not.** Reproduced against the current tool:

```
$ printf 'projects/m7-ai-assisted/FEATURE-BACKLOG.md\nprojects/m8-ownership/README.md\n' \
    | poetry run python tools/changed_projects.py --from-stdin
["projects/m7-ai-assisted", "projects/m8-ownership"]
```

`student-check.yml` feeds that list straight into a build matrix whose first step is
`chmod +x gradlew` in each directory. Neither ships a `gradlew`. So the first student pull
request touching an M7 or M8 file fails CI with:

```
chmod: cannot access 'gradlew': No such file or directory
```

A failure that has nothing to do with the student's work, arriving on `main`. This is the
clean-clone invariant's concern in a different costume — §12.3 exists because *a student cannot
tell a broken toolchain from their own mistake*, and this produces exactly that confusion for a
student whose only change was to a Markdown file.

**The module is tested, and the tests miss it.** `tests/test_changed_projects.py` carries eight
tests of `milestone_dirs`, none covering a directory without a `settings.gradle`. Note that
`test_prose_change_selects_nothing` does *not* contradict the reproduction above: it asserts
about prose paths outside `projects/` entirely (`README.md`, a docs path), not a Markdown file
inside a project directory. And `test_file_directly_in_projects_root_selects_nothing` covers
`projects/README.md`, which the existing `len(parts) >= 3` guard already handles. The
three-part case is simply not covered by anything.

**Fix:** require `settings.gradle` to exist before selecting a directory, and add a pytest
regression asserting that M7/M8-shaped paths are excluded while `projects/testouts/<fixture>/`
paths still are not. The regression must be shown failing against the unfixed tool — a guard
nobody has seen fail is a guard nobody knows works.

**Two constraints on that fix, both found while checking it:**

1. **It makes `milestone_dirs` filesystem-dependent**, where today it is pure string
   manipulation over the changed-path list. Take an injectable repository root parameter
   defaulting to the real root, the way `tests_lock.py` does, so the new tests can build
   fixture trees under `tmp_path` rather than depending on the checkout.
2. **`test_deleted_paths_are_still_selected` still passes, and the reason is worth knowing.**
   It deletes a file *inside* `m2-oop`, whose `settings.gradle` is still on disk, so the
   directory is still selected. Only deleting an entire project changes behaviour — and there
   dropping it is correct, because there is no longer anything to build. Do not weaken the
   check to preserve a case that wants the new behaviour.

## 4. `Robot-2026` mining — what M7 features actually exist

Read at `28ce5397d88275001d656dbb717d22cf9ac0150d`.

**The strongest candidate: `VisionSubsystem`'s rejection counters are write-only.** The file
declares twelve `private long` counters — accepted, rejected-total, rejected-due-to-ambiguity,
and rejected-due-to-jumping, for each of three cameras — and increments them, with Javadoc
stating they are *"Used for telemetry"* and *"Tracks telemetry for monitoring."* Verified: they
have no public accessor, no other file in the repository references them, and the file's only
`// Update telemetry` comment assigns to unrelated drift fields. Nothing publishes them
anywhere.

That is a genuinely good M7 feature — small, real, useful, defensible under questioning, and
testable without hardware. It is also the exact code M5's `READING.md` already sends students to
study, so an M7 student meets it a second time with the context to improve it.

**Second: `DriveState.java:52` carries a bare `// TODO add to log`.**

**Tuning TODOs are not features and the backlog must say so.** `IndexerConstants.java:16`,
`ShooterConstants.java:111`, `VisionConstants.java:28` and others are `TODO: tune` markers.
Tuning is M4's lesson and requires hardware; none belongs in an M7 backlog.

**Constraint worth stating in the file: `Robot-2026` has zero tests.** `git ls-tree` reports no
files under `src/test`. The harness is wired — `build.gradle` has
`org.junit.jupiter:junit-jupiter:5.10.1` and `useJUnitPlatform()`, the same pinned version this
repository uses — so M7's DoD item *"Tests pass and cover the new behavior"* is satisfiable, but
a student's feature will likely create the repository's first `src/test/`. The backlog should
favour features testable without hardware, and say why.

## 6. Verification strategy

The clean-clone invariant does not apply — there is no Gradle project to assemble and no given
test to go red. What replaces it:

- **`templates_sync.py` proven to fail on drift.** Edit one fenced block, confirm `verify`
  exits non-zero naming the file, restore, confirm it passes. The `tests_lock` tamper proof,
  applied to the thing this milestone actually guards.
- **The `changed_projects` regression proven to fail first.** Run the new test against the
  unfixed tool and watch it fail, then fix and watch it pass.
- **M7 and M8 land in no `skeleton-integrity` branch at all.** They have no `settings.gradle`,
  so the workflow's `find` never discovers them. Confirm by reading the discovery, and confirm
  `student-check.yml` no longer selects them.
- **Every pinned reference resolves.** Each of the four copied files and every symbol
  `DEFENSE-REVIEW.md` or `FEATURE-BACKLOG.md` names must exist at the pinned SHA, checked the
  way M5's `READING.md` symbols were.
- **`mkdocs build --strict` and `site_guard`** — `templates/` is outside `docs_dir` and must
  stay unpublishable structurally.
